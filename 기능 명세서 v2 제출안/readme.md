# 챙겨요 체크리스트 생성 DB — 전체 문서

여행 조건 몇 가지를 넣으면 **"무엇을 챙겨야 하는지, 왜 챙겨야 하는지"** 목록이 나오도록 만든 데이터입니다.
CSV 20장으로 되어 있고, RDB는 아니지만 각 파일이 관계형 테이블처럼 PK/FK로 조인되도록 설계했습니다.

> 개발·유지보수용 문서입니다. 스키마·스크립트·편집 규칙까지 전부 다룹니다.
> 데이터가 무엇을 할 수 있는지만 빠르게 보려면 **[`readme_개요.md`](readme_개요.md)** 를 보세요.

```
목적지 국가 ┐
여행 날짜  ├─▶  [ 이 DB ]  ─▶  섹션별 준비물 목록 + 항목마다 "왜 필요한지"
동반자    │                    필수 / 기본 짐싸기 / 액티비티 종류별
액티비티   ┘
```

**날씨와 기온은 입력받지 않습니다.** 목적지와 날짜로 추정합니다(→ [6장](#6-날씨와-기온은-어떻게-정하나)).

## 1. 읽기 전에 알아야 할 3가지

**① 인코딩은 UTF-8 BOM입니다.** 파이썬은 `encoding="utf-8-sig"` 로 열어야 첫 컬럼명 앞에 `﻿` 가 붙지 않습니다. 엑셀에서 더블클릭해도 한글이 깨지지 않습니다.

**② `_NAME_TEMP` 로 끝나는 컬럼은 읽는 시점에 버리세요.** `item_id` 옆의 `item_id_NAME_TEMP` 처럼, CSV를 사람이 눈으로 편집할 때 `I0033` 이 「카메라」라는 걸 알 수 있도록 붙여 둔 **보조 컬럼**입니다. 값은 항상 대응하는 마스터 테이블에서 그대로 복사한 것이라 정보가 늘지 않습니다.

```python
{k: v for k, v in row.items() if not k.endswith("_NAME_TEMP")}
```

**③ 값 하나에 여러 개가 들어가는 컬럼은 `;` 로 구분합니다.** `climate_normal_period.weather_condition_ids`(`sunny;rain`)와 `dim_item_category.source_rule_table` 이 여기 해당합니다. **나열 순서에 의미가 있으니**(→ [5장 3단계](#3단계-겹치는-아이템을-하나로-접는다)) 정렬하지 마세요.

## 2. 설계 원칙 — 왜 이렇게 생겼나

이 스키마의 모양은 대부분 **제품 결정의 결과**입니다. 데이터를 고치기 전에 이 장을 먼저 읽으면 "왜 이 컬럼이 없지?" 하는 대부분의 의문이 풀립니다.

### ① "무엇을 챙기는가"와 "왜 챙기는가"를 분리했습니다

같은 아이템이라도 국가 때문에 필요할 수도, 액티비티 때문에 필요할 수도 있고 **그때마다 근거가 달라야 합니다.** 그래서 아이템은 `item_master.csv` 한 곳에만 정의하고, "이 조건에서는 이 이유로 필요하다"는 `rule_*` 테이블의 행으로 표현합니다. 아이템 하나가 규칙 여러 개에 등장하는 것이 정상입니다.

### ② 준비물에 순위를 매기지 않습니다

이전에는 `necessity_level`(필수/권장/선택/불필요/반입주의) 컬럼이 있었지만 **통째로 제거했습니다.**

- **제품 판단** — "필수/권장/선택"은 서비스가 사용자 대신 내리는 판단인데, 무엇이 필수인지는 사람마다 다릅니다. 잘못 단정하면 오히려 신뢰를 잃습니다. **근거만 주고 판단은 사용자가 하게 합니다.**
- **스키마 판단** — 한 컬럼에 "순위"(필수/권장/선택)와 "순위가 아닌 신호"(반입 금지, 안 챙겨도 됨)가 섞여 있었습니다. 순위를 없애기로 한 이상 절반만 남길 수 없었습니다.

그래서 지금 규칙 행이 갖는 것은 **아이템 + 근거 코멘트뿐**입니다. 중요도, "안 챙겨도 되는 이유", 반입 제한은 전부 `reason_comment` 문장 안에서 전달합니다.

> **남는 영향** — 경고 배지·취소선처럼 렌더링을 분기할 기계적 근거가 없습니다. 다시 필요해지면 순위 컬럼을 되살리지 말고 **비순위 플래그 컬럼**을 새로 설계하세요(→ [9장](#9-확장-시-체크리스트)).

### ③ 수량은 세지 않습니다

아이템은 "필요/불필요"만 판단하면 되고, 몇 개·몇 벌인지는 체크리스트가 알려주지 않습니다. `quantity` 계열 필드와 `item_master.unit`(개/벌/켤레)을 모두 제거한 이유입니다.

### ④ "필수"와 "기본"은 별개입니다

둘 다 조건 없이 항상 매칭되지만 의미가 다릅니다.

| | 뜻 | 예 |
|---|---|---|
| `rule_essential_item` | 없으면 **여행 자체가 불가능**한 것 | 여권, 항공권, 해외 결제 가능 카드, 환전, eSIM |
| `rule_base_item` | 없어도 여행은 되지만 **보통 챙기는** 것 | 여행자보험, 상비약, 기초 세면도구 |

원래는 한 테이블이었는데, "조건 없이 항상 필요하다"는 이유만으로 여권과 상비약이 같은 칸에 있는 게 맞지 않아 나눴습니다. 화면에서도 서로 다른 섹션입니다.

### ⑤ 화면 섹션은 세 갈래뿐입니다 — 필수 / 기본 짐싸기 / 액티비티 종류별

국가·동반·날씨·온도 규칙에 걸린 아이템은 **자기 섹션을 만들지 않고 전부 「기본 짐싸기」로 합류합니다.** 여행 조건 때문에 추가됐다는 사실은 `reason_comment` 가 이미 설명하므로, 섹션까지 나누면 화면이 잘게 쪼개지고 섹션당 1~2개짜리 토막만 늘어납니다.

**액티비티만 예외로 종류별 섹션이 따로 납니다.** 화면에 "액티비티"라는 뭉뚱그린 이름 대신 "수영·물놀이", "캠핑" 같은 구체적인 제목이 떠야 하기 때문입니다. 그래서 `dim_item_category` 는 (필수/기본) 2 + 액티비티 10 = **12행**입니다.

### ⑥ 액티비티는 "준비물이 있는가"를 기준으로 고릅니다

`dim_activity` 에는 아무 활동이나 넣지 않고 **그 활동을 하면 고정적으로나 추가적으로 필요한 준비물이 있는 것만** 담습니다. 시내 관광·쇼핑처럼 특별한 준비물이 없는 활동은 제외했습니다. 현재 10종이고, 10종 모두 `rule_activity_item` 에 실제 규칙이 5~12행씩 채워져 있습니다.

### ⑦ 코멘트에 카테고리명을 다시 밝히지 않습니다

섹션 제목이 이미 카테고리를 나타냅니다. 그리고 한 아이템이 여러 카테고리에 걸쳐 매칭되더라도 **화면에 실제로 표시되는 그 카테고리의 코멘트만** 보여줍니다.

### 3-4. 링크 — "그걸 어디서 더 알아보나"

일부 아이템은 눌렀을 때 정보 글이나 예약 페이지로 넘어가는 **링크 시트**(바텀시트)를 띄웁니다. 트리플에 이미 해당 콘텐츠가 있는 아이템을 체크리스트에서 그 글로 이어주기 위한 데이터입니다.

| 파일 | PK | 행 | 설명 |
|---|---|---|---|
| `item_link.csv` | link_id | 6 | 시트에 뜨는 줄. `item_id` 당 0~N행 |

| 컬럼 | 뜻 |
|---|---|
| `display_order` | 시트 안에서의 순서 |
| `link_type` | `info`(읽는 글) / `booking`(예약·가입 등 판매 연결) |
| `link_text` | 줄에 표시할 문구 |
| `link_url` | 이동할 주소 |

**설계 의도**

- **컬럼이 아니라 행을 늘립니다.** `링크1~3` 컬럼을 붙이면 4번째 링크가 생기는 순간 스키마를 고쳐야 하고, 링크가 없는 127개 아이템에 빈 칸이 6개씩 생깁니다.
- **별도의 "시트 있음" 플래그를 두지 않았습니다.** 이 테이블에 행이 1개 이상이면 시트가 있는 것입니다.
- **`link_type` 을 나눈 이유** — 판매 링크 클릭은 **구매 의사 지표**로 세야 하지만 정보 링크 클릭은 아닙니다. 제휴·수수료 고지가 필요해지면 대상도 `booking` 행뿐입니다. 나중에 넣으면 기존 행을 다시 분류해야 해서 처음부터 넣었습니다.
- **하단 문구는 `item_master.link_note` 에 있습니다.** 아이템당 하나뿐이라 `item_link` 에 두면 링크마다 같은 문장이 반복됩니다.

**서비스에서 쓰는 법 — 두 단계로 나뉩니다**

**① 목록 화면에서 「링크 아이콘을 띄울지」는 `item_master` 만 보고 판단합니다.**

```
link_note 에 텍스트가 있거나  또는  link_count 가 1 이상   →   링크 아이콘 표시
```

```python
has_link = bool(item["link_note"]) or int(item["link_count"] or 0) >= 1
```

목록은 한 화면에 50~70개 항목을 그리므로, **행마다 `item_link` 를 뒤지지 않고 마스터에 이미 있는 두 값으로 끝냅니다.** 두 조건을 `또는` 으로 묶은 것은 안전장치입니다 — `link_count` 는 파생 값이라 동기화를 빠뜨리면 비어 있을 수 있는데, 그때도 손으로 적은 `link_note` 가 있으면 아이콘을 살립니다. (현재 데이터에서는 `link_note` 가 있는 2행 모두 `link_count` 도 채워져 있어 두 조건이 같은 결과를 냅니다.)

**② 시트를 실제로 열 때 「무엇을 보여줄지」는 `item_link` 를 조회합니다.**

```python
links = [r for r in read_csv("item_link.csv") if r["item_id"] == item_id]
links.sort(key=lambda r: int(r["display_order"]))
open_sheet(links, note=item["link_note"])
```

⚠️ **이 규칙 때문에 `link_count` 가 화면에 직접 영향을 줍니다.** `item_link.csv` 에 행을 넣고 동기화를 빠뜨리면 **링크가 있는데도 아이콘이 안 뜹니다**(그 아이템에 `link_note` 까지 없다면). `item_link.csv` 를 고친 뒤에는 반드시 `_build\run_sync_link_count.bat /w` 를 돌리세요 → [10장](#10-유지보수).

**화면 설계 연결 — `C-05` 정보 안내 모달** (변경 번호 `CHG-022`)

기능명세서상 이 데이터가 그려지는 화면은 **`C-05` 정보 안내 모달**입니다. 진입점은 `C-01` 체크리스트 화면의 **6번 요소(링크 아이콘)** 이고, 아이콘이 붙은 아이템을 누르면 모달이 열립니다.

| 모달 구성 요소 | 참조하는 값 |
|---|---|
| 리스트 **개수** | `item_master.csv` 의 `link_count` |
| 리스트 **순서** | `item_link.csv` 의 `display_order` |
| 링크 **텍스트** | `item_link.csv` 의 `link_text` |
| 링크 **주소** | `item_link.csv` 의 `link_url` |
| 리스트 하단 **안내 문구** | `item_master.csv` 의 `link_note` — 값이 있는 경우에만 표시 |

리스트를 누르면 해당 주소로 이동합니다. 하단 안내 문구는 리스트 아래에 고정으로 붙고, `link_note` 가 비어 있으면 영역 자체가 나오지 않습니다.

> **개수와 실제 줄이 서로 다른 파일에서 옵니다.** 개수는 마스터의 `link_count`, 줄의 내용은 `item_link` 입니다. 두 값이 어긋나면 **줄이 잘리거나 빈 줄이 생깁니다** — 동기화 스크립트가 이 일치를 보장하는 유일한 장치이므로, `item_link.csv` 를 고친 뒤에는 반드시 돌려야 합니다.

### 3-6. 삭제율 — "다른 사람들은 이걸 뺐나"

편집 모드에서 **"많은 사람이 두고 갔어요"** 코멘트를 띄울지 판단하는 집계 값입니다. 화면 설계 `E-01` 4번 요소에 해당합니다.

| 파일 | PK | 행 | 설명 |
|---|---|---|---|
| `item_delete_rate.csv` | stat_id | 0 (집계 전) | 액티비티로 추가된 아이템의 삭제율. **배치로 다시 계산하는 파생 테이블** |

| 컬럼 | 뜻 |
|---|---|
| `activity_id` · `item_id` | 집계 대상. 둘의 조합이 곧 `rule_activity_item` 한 행에 대응합니다 |
| `exposure_count` | 유효 노출 건수 (분모) |
| `delete_count` | 유효 삭제 건수 (분자) |
| `delete_rate` | `delete_count / exposure_count`, 소수 셋째 자리까지 |
| `comment_shown` | 노출 조건을 모두 만족하면 `Y`. 클라이언트는 이 값만 보면 됩니다 |
| `updated_at` | 마지막 집계 시각 (`YYYY-MM-DD`) |

#### 왜 액티비티 단위인가

**액티비티로 추가된 아이템만 집계합니다.** 필수·기본·국가·날씨 규칙으로 들어온 항목은 대상이 아닙니다. 이유는 두 가지입니다.

- **필수·국가·날씨는 삭제가 신호가 아닙니다.** "여권"을 지운 사람은 추천이 틀렸다고 말하는 게 아니라 이미 챙겼다는 뜻입니다.
- **액티비티는 사용자가 스스로 고른 조건**입니다. "캠핑을 고른 사람 중 몇 %가 이 항목을 뺐는가"는 곧 "이 액티비티 규칙이 과했는가"이고, 그게 이 지표로 답하려는 질문입니다.

집계 단위도 **여행 안의 액티비티 단위**이지 사용자 단위가 아닙니다. 같은 사람이 캠핑 여행을 세 번 가면 3건으로 셉니다. 그래서 키가 `(activity_id, item_id)` 이고, 같은 아이템이라도 **캠핑에서의 삭제율과 골프에서의 삭제율이 서로 다른 행**입니다.

#### 계산식

```
삭제율 = 유효 삭제 건수 / 유효 노출 건수
```

| | 세는 것 | 제외하는 것 |
|---|---|---|
| **유효 삭제** | 항목을 **개별로** 지운 건수 | · 카테고리 일괄 삭제<br>· 리스트 초기화·재생성에 의한 삭제<br>· 실행 취소(Undo)로 되돌려진 삭제 |
| **유효 노출** | 그 항목이 생성된 여행 수 | · 그 항목이 포함된 카테고리가 일괄 삭제된 경우<br>· 여행 일정 자체가 삭제된 경우 |

**제외 항목이 이 계산식의 핵심입니다.** 일괄 삭제와 재생성은 "이 항목이 불필요하다"가 아니라 "이 묶음이 통째로 필요 없다" 또는 "다시 만들겠다"는 행동이라, 항목 단위 신호로 섞이면 삭제율이 실제보다 부풀려집니다. Undo는 사용자가 스스로 취소한 것이므로 애초에 삭제가 아닙니다.

분모에서도 같은 케이스를 빼는 이유는 **분자와 분모의 모집단을 맞추기 위해서**입니다. 일괄 삭제된 노출을 분모에 남기면, 분자에서 제외한 삭제가 분모에만 남아 삭제율이 실제보다 낮게 나옵니다.

#### 코멘트 노출 조건

네 가지를 **모두** 만족할 때만 띄웁니다. `comment_shown` 컬럼이 이 판정 결과입니다.

| 조건 | 값 |
|---|---|
| 삭제율 | **70% 이상** |
| 표본(유효 노출) | **30건 이상** |
| 화면 | **편집 모드 진입 시에만** |
| 대상 | 액티비티로 추가된 항목만 |

표본 하한이 있는 이유는, 노출 5건 중 4건이 삭제된 항목에 "5명 중 4명은 두고 갔어요"라고 쓰면 **사실이 아닌 문장**이 되기 때문입니다. 30건 미만이면 행은 있어도 `comment_shown = N` 입니다.

문구 자체는 이 테이블에 담지 않습니다. `delete_rate` 만 주고 **문장은 클라이언트가 만듭니다** — 같은 문장이 84행에 중복 저장되는 것을 피하고, 카피를 바꿀 때 데이터를 다시 만들지 않아도 되기 때문입니다.

#### 원천 로그는 이 파일이 아닙니다

`item_delete_rate.csv` 는 **결과만** 담습니다. 위 계산식을 돌리려면 아래 성격의 이벤트 로그가 서버(또는 GA4)에 따로 쌓여야 합니다. CSV로 관리할 데이터가 아니라 여기서는 스키마만 적어 둡니다.

| 필드 | 뜻 |
|---|---|
| `trip_id` | 여행 단위 식별자 — **집계 단위의 기준** |
| `item_id` · `source_activity_id` | 어떤 항목이 어느 액티비티 때문에 들어왔는지 |
| `event_type` | `exposed`(생성 시 목록에 포함) / `deleted` / `restored` |
| `delete_scope` | `single` / `category_bulk` / `regenerate` / `trip_delete` — **`single` 만 유효 삭제** |
| `is_undone` | 실행 취소로 되돌려졌는지 |
| `occurred_at` | 발생 시각 |

집계 배치는 이 로그에서 `delete_scope = single AND is_undone = false` 인 건수를 분자로, `exposed` 중 `category_bulk`·`trip_delete` 에 휩쓸리지 않은 건수를 분모로 세어 `item_delete_rate.csv` 를 다시 씁니다.

## 5. 체크리스트 만드는 법

`share/example_generate.py` 가 아래를 그대로 구현한 참조 구현입니다(약 100줄, 표준 라이브러리만).

### 입력

| 값 | 어디서 오나 |
|---|---|
| `country_id` | 사용자가 고른 목적지 |
| `companion_id` | 사용자가 고른 동반자 |
| `activity_ids` | 사용자가 고른 액티비티 (0개 이상) |
| `weather_condition_ids` | **추정** → [6장](#6-날씨와-기온은-어떻게-정하나) |
| `temp_band_id` | **추정** → [6장](#6-날씨와-기온은-어떻게-정하나) |

여행 기간은 입력만 받고 생성 로직에는 쓰지 않습니다. 어디에도 FK로 연결되어 있지 않습니다.

### 1단계: 조건에 걸리는 규칙을 모두 모은다

7개 규칙 테이블을 각자의 FK로 거릅니다. `essential` 과 `base` 는 조건이 없으니 전부 가져옵니다. 이때 각 매치에 **화면 섹션(`category_id`)** 을 함께 붙입니다.

| 규칙 테이블 | 붙는 category_id |
|---|---|
| `rule_essential_item` | `essential` |
| `rule_base_item` · `rule_country_item` · `rule_companion_item` · `rule_weather_item` · `rule_temp_item` | 전부 `base` |
| `rule_activity_item` | 그 행의 `activity_id` 값 그대로 (`swimming`, `camping` …) |

### 2단계: 아이템별로 노출 섹션을 하나 고른다

이번 생성에서 실제로 매칭된 `category_id` 들 중 **`match_priority` 가 가장 낮은(=우선순위가 가장 높은)** 것 하나만 남깁니다. `display_order` 가 아닙니다.

> **예 — 방수팩.** "수영·물놀이" 액티비티 규칙과 "비" 날씨 규칙 양쪽에 걸립니다. 액티비티(6)가 기본(12)보다 우선순위가 높으므로 **「수영·물놀이」 섹션에만 1회** 노출되고 기본 짐싸기에는 다시 나오지 않습니다.

이 규칙 때문에 **`rule_activity_item` 에 아이템을 추가한다는 것은 "그 액티비티를 고른 여행에서는 이 아이템이 기본 짐싸기에서 사라지고 액티비티 섹션으로 옮겨간다"는 뜻**입니다. 그 액티비티를 고르지 않은 여행에서는 원래대로 기본 짐싸기에 나옵니다.

### 3단계: 겹치는 아이템을 하나로 접는다

노출 섹션이 정해지면, **그 섹션에서 나온 코멘트만** 남깁니다. 화면에 뜨지 않는 섹션의 코멘트는 버립니다.

`base` 는 규칙 테이블 5장이 합쳐진 섹션이라 한 아이템에 코멘트가 여러 개 걸릴 수 있습니다(예: "경량 패딩·방한복" = 국가 + 날씨 + 온도). 이때는 `dim_item_category.base` 행의 `source_rule_table` 에 적힌 순서대로 **가장 앞선 것 하나만** 씁니다.

```
국가 > 동반 > 날씨 > 온도 > 기본
```

더 구체적인 조건에서 나온 근거가 더 유용하다고 봤기 때문입니다. 순서를 바꾸려면 CSV의 문자열 순서만 고치면 됩니다.

> **따라서 `rule_base_item` 의 코멘트는 "가장 약한 근거"입니다.** 같은 아이템이 국가·날씨 규칙에도 있으면 화면에 뜨지 않습니다. `base` 에는 "어느 여행에나 같은 이유로 필요한 것"만 넣고, 조건에 따라 이유가 달라지는 것은 해당 조건 테이블에 적으세요.

### 4단계: 정렬해서 섹션별로 묶는다

섹션은 `display_order` 순(필수 → 기본 → 액티비티), 섹션 안에서는 규칙 테이블에 적힌 행 순서를 그대로 유지합니다.

### 의사코드

```
matched = {}   # item_id -> [(category_id, source_rule_table, comment), ...]

rule_essential_item  전체            → category_id = "essential"
rule_base_item       전체            → category_id = "base"
rule_country_item    country_id 일치  → category_id = "base"
rule_companion_item  companion_id 일치 → category_id = "base"
rule_weather_item    weather_id ∈ 입력 → category_id = "base"
rule_temp_item       temp_band_id 일치 → category_id = "base"
rule_activity_item   activity_id ∈ 입력 → category_id = 그 행의 activity_id

각 item_id 에 대해:
    노출 섹션 = 매칭된 category_id 중 match_priority 최소값
    노출 코멘트 = 그 섹션에서 나온 매치 중 source_rule_table 순서가 가장 앞선 것 1개
    item_master 조인 → item_name, item_desc, is_purchasable, link_count, link_note

display_order 로 섹션 정렬 → 섹션별로 묶어 반환
```

## 6. 날씨와 기온은 어떻게 정하나

사용자에게 묻지 않고 **목적지와 날짜로 추정**합니다. 경로가 두 개입니다.

```
출발까지 16일 이내  →  Open-Meteo 예보 API
출발까지 16일 초과  →  climate_normal_period.csv (평년값 폴백)
API 호출 실패      →  climate_normal_period.csv
```

### 왜 판정 기준이 두 벌인가

`dim_weather_condition.csv` 는 같은 "비"를 판정하는 기준을 **예보용과 평년값용으로 따로** 갖습니다. 이건 실수가 아니라 필수입니다.

**Open-Meteo의 일별 `weather_code` 는 「그날 가장 심한 날씨」입니다.** 하루 중 5분만 비가 와도 그날은 비로 기록됩니다.

- **예보 경로에서는 이게 오히려 맞습니다.** 특정 여행일 하루에 대해서는 「그날 조금이라도 비가 오는가」가 알맞은 질문이기 때문입니다.
- **평년값 경로에서는 완전히 틀립니다.** 10년치를 이 코드로 집계하면 거의 모든 순이 `rain` 으로 칠해집니다. 실제로 첫 실행에서 **비가 90.5%** 로 나왔습니다.

그래서 평년값은 `weather_code` 를 버리고 **물리량 기준**으로 다시 판정합니다.

| 컬럼 | 하는 일 |
|---|---|
| `forecast_source` | 예보 경로에서 볼 값 (대부분 `weather_code`, 바람만 `wind_speed_10m_max`) |
| `wind_min_kmh` | 예보 경로의 `windy` 판정 임계값 |
| `normal_source` | 평년값 경로에서 볼 물리량 |
| `normal_agg` | 집계 방식 — `mean`(구간 평균) / `day_ratio`(조건을 만족한 날의 비율) |
| `normal_op` · `normal_threshold` | 비교 연산자와 임계값 |
| `normal_min_ratio` | `day_ratio` 일 때, 이 비율을 넘어야 그 상태로 인정 |

**현재 값**

| 상태 | 평년값 판정 |
|---|---|
| 맑음 | 구간 평균 일조율 ≥ 0.55 |
| 구름 | 구간 평균 일조율 < 0.35 |
| 바람 | 일최대풍속 30km/h 이상인 날이 25% 이상 |
| 비 | 일강수 1.0mm 이상인 날이 30% 이상 |
| 눈 | 일강설 1.0cm 이상인 날이 10% 이상 |

맑음·구름만 **구간 평균(`mean`)** 을 쓰는 이유는 둘이 상호배타적이어야 하기 때문입니다. "맑은 날이 25% 이상"처럼 날짜 비율로 재면 맑음과 구름이 동시에 붙습니다. 비·눈·바람은 반대로 **몇 퍼센트의 날에 일어나는가**가 본질이라 `day_ratio` 를 씁니다.

> `windy` 의 30km/h는 아직 **근거 없는 초기값**입니다. `fill_climate_normals.py --stats` 로 실측 분포를 뽑아 조정하세요.

### 왜 월이 아니라 순(旬)인가

월 단위는 4월 초와 4월 말을 같은 값으로 취급합니다. 반대로 7일·15일 단위는 월 경계와 어긋나 날짜 계산이 지저분해집니다. **순(旬)은 월 경계와 정확히 맞아떨어지면서 월보다 3배 촘촘합니다.**

`climate_normal_period.day_from`/`day_to` 는 **그 달에서 이 순이 실제로 덮는 날짜**라 하순은 달마다 다릅니다(28·30·31일, 2월은 윤일까지 포함해 29). 덕분에 출발일이 어느 행에 걸리는지는 **숫자 비교만으로** 판정됩니다.

```python
month == 입력월 and day_from <= 입력일 <= day_to
```

`dim_period.csv` 의 하순 `day_to` 가 31인 것은 **달 길이를 모르는 테이블이라 적어 둔 상한**입니다. 실제 말일은 `climate_normal_period` 쪽이 월별로 갖습니다.

### 온도 구간

`temp_min_c` / `temp_max_c` 를 `dim_temp_band` 에 넣어 구간 하나를 고릅니다.

```
최저기온 < 5      → low
최고기온 ≥ 26     → high
그 외             → mid
```

```
_build\run_singapore.bat                싱가포르만 (429 대응)

```

## 7. 데이터 작성 원칙

- **이유가 자명한 항목은 `reason_comment` 를 비웁니다.** 여권·항공권·충전기·속옷처럼 이름만 보면 되는 항목에 굳이 설명을 달면 화면만 길어집니다. 코멘트는 **사용자가 몰랐을 정보가 있을 때만** 답니다. (현재 248행 중 223행에 코멘트가 있습니다.)
- **`reason_comment` 는 50자 내외로 씁니다.** 한 문장, 길어도 두 문장. 현재 평균 38자입니다.
- **단, 안전·법적 정보는 예외로 길어도 됩니다.** 통관 금지, 의약품 반입 한도, 전자담배·드론 법규, 항공 배터리 규정, 감염병, 면허·의무 신고처럼 **조건·수치·처벌이 빠지면 사용자가 실제 불이익을 보는** 내용은 길이보다 정확도를 우선합니다. 현재 50자를 넘는 32행이 여기 해당합니다.
- **"넉넉하게, 충분한 수준을 조금 넘어서"가 제품 방향입니다.** 애매한 항목도 빼지 말고 넣되 판단 근거를 코멘트에 적어, 사용자가 읽고 직접 지우게 합니다. 애매하다는 사실 자체를 적어 주세요 — 예: "필요한 분만 챙기면 돼요."
- **"안 가져가도 된다"는 정보를 적극적으로 씁니다.** "현지에서 빌리거나 제공되니 안 가져가도 된다"고 알려주는 것이 이 기능의 가장 큰 차별점입니다(스키 장비, 스키복, 온천 목욕타월 등). 짐 무게를 실제로 줄여주는 정보입니다.
- **반입 제한은 국가별 통관 규정과 시설 반입 규정 양쪽에 씁니다.** 지금은 이 신호를 구분하는 컬럼이 없으므로 **금지·주의 문구를 `reason_comment` 안에 반드시 명시**해야 합니다.

## 9. 확장 시 체크리스트

| 하려는 일 | 해야 할 것 |
|---|---|
| 새 국가 추가 | `dim_country.csv` 에 행 추가 + `rule_country_item.csv` 에 필요한 만큼 행 추가 |
| 새 아이템 추가 | `item_master.csv` 에 행 추가 → **왜 필요한지에 따라** 알맞은 `rule_*` 에 행 추가 → `item_category_map.csv` 에도 매핑 행 추가 |
| 새 액티비티 종류 추가 | `dim_activity.csv` + `dim_item_category.csv`(`display_order`·`match_priority` 포함) + `rule_activity_item.csv` |
| 새 조건 차원 추가 (예: 숙소유형) | `dim_*` 1장 + `rule_*_item.csv` 1장. **기본값은 「기본 짐싸기로 합류」** — `dim_item_category` 의 `base` 행 `source_rule_table` 끝에 `;` 로 이름만 덧붙이면 됩니다(붙인 위치가 곧 코멘트 우선순위). 전용 섹션이 필요할 때만 `dim_item_category` 에 행을 추가 |
| 섹션 노출 **순서** 변경 | `dim_item_category.display_order` 만 조정 (코드 변경 불필요) |
| 겹칠 때 **이기는 섹션** 변경 | `dim_item_category.match_priority` 만 조정 |
| `base` 안 코멘트 우선순위 변경 | `dim_item_category.base` 행의 `source_rule_table` 나열 순서 조정 |
| 아이템에 링크 붙이기 | `item_link.csv` 에 행 추가 → `_build\run_sync_link_count.bat /w` 실행 |
| 삭제율 코멘트 임계값 조정 | 집계 배치의 상수(70% · 30건)를 고치고 `item_delete_rate.csv` 를 다시 생성. **CSV를 손으로 고치지 마세요** — 다음 집계에서 덮어써집니다 |
| 반입금지·불필요 같은 신호 구분 부활 | 순위 컬럼(`necessity_level`)을 되살리지 말고 **비순위 플래그 컬럼**을 새로 설계 (예: `item_flag` = `normal`/`caution`/`not_needed`). 옛 컬럼의 문제는 "순위"와 "신호"를 한 칸에 섞은 것이었습니다 |

**새 아이템을 어느 규칙 테이블에 넣을지**

- 없으면 여행 자체가 불가능 → `rule_essential_item`
- 보통 챙기지만 없어도 여행은 가능 → `rule_base_item`
- **조건이 있으면 조건 테이블에 넣는 쪽이 항상 낫습니다.** 화면에는 똑같이 기본 짐싸기로 나오지만 코멘트가 더 구체적이고 우선순위도 앞섭니다.
